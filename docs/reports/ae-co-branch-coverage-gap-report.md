# AE / CO coverage gap report — Issue #318

Gap analysis for "Enhance the list of Assessed elements and Contingencies": for every grid,
every branch (ACLineSegment, 2W/3W PowerTransformer) at or above 110 kV should have an
`nc:AssessedElement` (AE profile) and an `nc:OrdinaryContingency` (CO profile).

Generated by cross-referencing each grid's EQ file (BaseVoltage per ACLineSegment /
PowerTransformerEnd, resolved against `Instance/commonData/Grid/cimxml/Grid_CommonData_CGM-CD.xml`)
against `nc:AssessedElement.ConductingEquipment` in `*_AE.xml` and
`cim:ContingencyEquipment.Equipment` in `*_CO.xml`.

## RDF/XML shape (from Belgovia, the most complete example)

**AssessedElement** (`Instance/Belgovia/NetworkCode/cimxml/Belgovia_AE.xml`):
```xml
<nc:AssessedElement rdf:ID="_<uuid>">
  <nc:AssessedElement.AssessedSystemOperator rdf:resource="#_<operator-uuid>"/>
  <nc:AssessedElement.ConductingEquipment rdf:resource="#_<branch-mRID>"/>
  <nc:AssessedElement.ScannedForRegion rdf:resource="#_<region-uuid>"/>
  <nc:AssessedElement.inBaseCase>true</nc:AssessedElement.inBaseCase>
  <cim:IdentifiedObject.description>...</cim:IdentifiedObject.description>
  <cim:IdentifiedObject.mRID><uuid></cim:IdentifiedObject.mRID>
  <cim:IdentifiedObject.name>AE<n></cim:IdentifiedObject.name>
  <nc:AssessedElement.normalEnabled>true</nc:AssessedElement.normalEnabled>
</nc:AssessedElement>
```
`OperationalLimit` and `SecuredForRegion` are optional (present on some, not others).
`rdf:ID` == `_` + `IdentifiedObject.mRID`. Names in existing data follow `AE<n>` sequentially per grid.

**OrdinaryContingency** (`Belgovia_CO.xml`) is two linked instances — a `cim:ContingencyEquipment`
naming the tripped branch, and an `nc:OrdinaryContingency`:
```xml
<cim:ContingencyEquipment rdf:ID="_<uuid>">
  <cim:ContingencyElement.Contingency rdf:resource="#_<contingency-uuid>"/>
  <cim:ContingencyEquipment.Equipment rdf:resource="#_<branch-mRID>"/>
  <cim:ContingencyEquipment.contingentStatus rdf:resource="https://cim.ucaiug.io/ns#ContingencyEquipmentStatusKind.outOfService"/>
  <cim:IdentifiedObject.description>...</cim:IdentifiedObject.description>
  <cim:IdentifiedObject.mRID><uuid></cim:IdentifiedObject.mRID>
  <cim:IdentifiedObject.name><branch short name></cim:IdentifiedObject.name>
</cim:ContingencyEquipment>
<nc:OrdinaryContingency rdf:ID="_<contingency-uuid>">
  <nc:Contingency.EquipmentOperator rdf:resource="#_<operator-uuid>"/>
  <nc:Contingency.normalMustStudy>true</nc:Contingency.normalMustStudy>
  <cim:IdentifiedObject.description>...</cim:IdentifiedObject.description>
  <cim:IdentifiedObject.mRID><uuid></cim:IdentifiedObject.mRID>
  <cim:IdentifiedObject.name>CO<n></cim:IdentifiedObject.name>
</nc:OrdinaryContingency>
```

**`.trig` files mirror the `.xml` files** (same triples in TriG syntax, generated — see
`semantic-tools/cim-trig.pl`). New entries need to land in both; the trig is very likely
regenerated from the xml by that script rather than hand-edited.

Espheim's model is a large synthetic transmission network (bus-numbered lines like `1-2`,
`23-25`, IEEE-style), which is why its branch count dwarfs the others. Svedala is similarly a
large realistic network; **26 of its 49 qualifying PowerTransformers are generator step-up
units** (names like `ATOMSBORG_G1_TRAFO`, `STUPET_G3_TRAFO` — HV side ≥110/135/220/400 kV, LV
side is a generator terminal at 17/20/50 kV). Espheim and Belgovia's qualifying transformers by
contrast look like genuine network autotransformers (e.g. Espheim `26-25` 220/132kV, Belgovia
`BO-TR2_2` 225/110kV).

## Open questions / decisions needed before implementation

1. **Do generator step-up (GSU) transformers count as "branches"?** The issue text says "every
   branch above and including 110kV (ACLineSegments, and 2W transformers...)" — read literally, a
   400/17kV GSU transformer qualifies (HV side ≥110kV). But a GSU is a radial connection to a
   single generator, not a transmission branch between two grid nodes, and is normally represented
   by generator contingencies, not branch contingencies. This one decision swings Svedala's count
   from 102 down to ~76 missing AE/CO (excluding GSUs), and likely affects Espheim too (needs the
   same check — not yet broken out, but its transformer names don't show the same `_G#_TRAFO`
   pattern, so it may be mostly real network transformers).
2. **Scale**: this is ~318 total missing AE + ~318 missing CO entries across Belgovia/Espheim/
   Svedala/Galia (before excluding any GSUs), each a full RDF instance pair with new UUIDs. This is
   not hand-authorable one-by-one at reasonable effort — implementation should be a script that
   reads each EQ file, finds uncovered ≥110kV branches, and generates/appends the AE and CO XML
   (and regenerates the matching `.trig`), rather than manually editing files branch-by-branch.
   Worth confirming with the user that a generation script (vs. a hand-picked subset of "important"
   branches) is the intended scope — the issue doesn't say "all", but literally says "for every...
   branch", which reads as exhaustive.
3. **Britheim has no `NetworkCode/` directory at all** (no AE.xml, CO.xml, or any other NC
   profile) — only `Grid/` (EQ/SSH/SV/TP). Adding AE/CO for its 4 branches means creating the
   `NetworkCode/cimxml/` (and `trig/`) directory and `manifest.ttl` from scratch, following the
   pattern of an existing grid's manifest — needs a dataset UUID, `dcat:Dataset` header, etc. Given
   it's only 4 branches this is low effort, but is new scaffolding, not just new file content.
4. **Nordheim has no branches and no NetworkCode dir** — it's a single-node network equivalent
   (one generator, one load, one equivalent injection, no ACLineSegment/PowerTransformer at all).
   Nothing to do for Nordheim under this issue; flagging so it isn't mistaken for missed work.
5. **Jotunheim** is a merged "GridSituation" combining Belgovia/Britheim/Espheim/Galia/Nordheim/
   Svedala/Portheim SSH snapshots at 30-minute intervals (`Instance/Jotunheim/Grid/cimxml/2D_*_SSH_2.xml`)
   plus `Instance/Jotunheim/NetworkCode/` holding IAM (Interconnector Availability?) and SAR
   (Security Analysis Result) files, not AE/CO. It has **no own AE/CO profile** — it reuses the
   per-grid ones. Out of scope for direct editing; once Britheim/Nordheim/per-grid AE/CO are
   updated, Jotunheim inherits the change automatically since it's a scenario built on top, not a
   duplicate model.
6. **Cross-border / HVDC contingency files** — `Svedala-Belgovia_CO.xml` (8 elements) and
   `DC-Espheim-Svedala_CO.xml` (4 elements) are separate CO datasets for tie-line/HVDC-adjacent
   contingencies (e.g. `CO_HVDC`, tie line `G1`). The DC interconnection pseudo-grids
   (DC-Espheim-Svedala, DC-Nordheim-Galia) contain only `DCLineSegment`/`VsConverter` HVDC
   equipment, no ACLineSegment/PowerTransformer — out of scope for this issue (issue explicitly
   scopes to ACLineSegments and transformers, not DC lines).
7. **Profile scaffolding consistency**: the four established grids' `NetworkCode/` directories do
   *not* share an identical profile set (Belgovia has ER/PS/RA/RAS/RAS_FAP/SHS/SIS; Espheim has
   ER/OR/RA/RAS/SIS/SSI; Svedala has AS/ER/FAP_PV/FAP_RAS_simple/RA/RAS_Jotunheim*/SIS/SSI; Galia
   has only ER/RA/RAS). **AE and CO are the only two profiles common to all four** — so for
   Britheim, only AE.xml + CO.xml (+ manifest) are strictly required for this issue; no other
   companion profile is implied by consistency with peers.

## Reproducing this analysis

A parsing script was used (BaseVoltage resolution + AE/CO cross-reference) — see conversation
history / re-derive with a similar script reading each grid's EQ file's `ACLineSegment` /
`PowerTransformer`+`PowerTransformerEnd` blocks, resolving `BaseVoltage` via
`Instance/commonData/Grid/cimxml/Grid_CommonData_CGM-CD.xml`, and diffing against
