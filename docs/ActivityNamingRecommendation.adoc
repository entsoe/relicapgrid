== Activity Naming Recommendation 

=== Purpose

The `prov:wasGeneratedBy` property provides an identifiable name for the activity that generated a dataset entity.

As dataset entities may contain instances conforming to one or more profiles, and the same profile may be generated in different operational or business contexts, the activity naming shall not be derived solely from profile names.

The purpose of the activity naming convention is to provide:

* a unique and stable identifier for the generating activity;
* a consistent and controlled vocabulary for provenance metadata;
* human-readable identifiers;
* identifiers that are interpretable by automated and AI-assisted tooling;
* sufficient contextual information to distinguish datasets generated for different purposes.

The activity naming represents the generating action, not the dataset structure.

=== Naming Structure

The recommended naming structure is:

[source]
----
<ActivityCode>-<ProfileCode>[-<ProcessCode>][-<TimeHorizonCode>][-<RunCode>]
----

Where:

* `ActivityCode` is mandatory;
* `ProfileCode` is mandatory;
* `ProcessCode` is optional;
* `TimeHorizonCode` is optional;
* `RunCode` is optional.

Elements shall appear in the defined order with the '-' as separator.

=== Naming Elements

[cols="1,1,4",options="header"]
|===
| Element | Cardinality | Description

| ActivityCode
| 1
| ActivityCode is the code that symbolism the activity type that represent the type of activity that produced/generated the entity.

| ProfileCode
| 1
| ProfileCode is the keyword for the given profile or dataset type that represent the content of the entity best.

| ProcessCode
| 0..1
| ProcessCode represent the business or application process/service that is the generated entity main purpose to support.

| TimeHorizonCode
| 0..1
| TimeHorizonCode represent the temporal duration that the entity is generated and when that entity is valid for.

| RunCode
| 0..1
| RunCode represent the repeated execution of the same ProcessCode and TimeHorizonCode.
|===

=== Activity Types

The `ActivityType` element identifies the nature of the activity that generated the dataset entity.

Its purpose is to distinguish datasets generated through different operational, analytical, planning, validation, or publication activities, even when the same profile is involved.

The activity type represents the semantic nature of the generating action, not the internal implementation or technical execution mechanism.

To support practical use in provenance metadata, dataset titles, and filenames, each activity type is associated with a compact activity code.

The compact activity code:

* shall be used in generated activity identifiers;
* shall be stable across implementations;
* shall remain concise and human-readable;
* shall avoid unnecessary verbosity in filenames and metadata values.

Tool implementations may present the full activity definition or description to users while storing or generating the compact code.

==== Controlled Vocabulary

The activity types are grouped into three families:

* *Modeling* — describe how the entity's content was produced
  (`SR`, `MA`, `AD`, `SD`, `FC`, `AC`);
* *Assessment* — describe a judgement or conformance result about content
  (`AS`, `VF`);
* *Transaction* — describe a transactional or dissemination act; the
  payload may itself have been produced by a modeling activity in a
  preceding, chained activity (`REQ`, `RES`, `PUB`).

`prov:wasGeneratedBy` shall reference the activity that *immediately* generated
the entity. A published analytical result therefore carries `PUB`; the
computation that produced its content is a separate, preceding activity.

=== Time Horizon

The `TimeHorizon` element identifies the temporal relationship between the generating activity and the operational delivery time or other relevant reference time.

Its purpose is to provide sufficient temporal context to distinguish otherwise identical activities and thereby support creation of unique, human-readable, and machine-friendly activity identifiers.

The `TimeHorizon` element is optional and shall only be included when required to distinguish activities.

==== Design Principles

The notation shall:

* be concise and human-readable;
* be deterministic and easy to interpret;
* be suitable for use in `prov:wasGeneratedBy`;
* be safe for reuse in dataset titles (`dcterms:title`) and physical file names;
* avoid special characters that may create interoperability or portability issues across tools, operating systems, scripting environments, and identifier processing;
* provide sufficient uniqueness for operational, planning, and settlement processes.

==== Naming Convention

The notation distinguishes three temporal contexts:

* pre-delivery activities;
* real-time activities;
* post-delivery activities.

The notation is inspired by ISO 8601 duration expressions, but intentionally simplified for operational readability and activity naming.

The format shall be one of:

----
<offset><unit>
<unit><offset>
RT
----

Where:

* `<offset><unit>` identifies time before delivery or reference time;
* `<unit><offset>` identifies time after delivery or reference time;
* `RT` identifies the real-time operational reference point.

Supported units:

* `H` — hour
* `D` — day
* `W` — week
* `M` — month
* `Y` — year

Special value:

* `RT` — real-time operational execution, observation, or snapshot

==== Rationale

===== ISO 8601 Inspiration and Simplification

The notation is conceptually inspired by ISO 8601 duration expressions, but intentionally simplified for operational naming purposes.

Examples:

* ISO 8601 `P1D` corresponds conceptually to `1D`
* ISO 8601 `PT6H` corresponds conceptually to `6H`

The ISO 8601 prefixes `P` (period) and `R` (recurrence) are intentionally not used because:

* their meaning is not immediately intuitive for many operational users;
* they add unnecessary verbosity to identifiers;
* the naming convention is intended for activity identification rather than formal temporal arithmetic;
* shorter identifiers improve readability in provenance metadata, dashboards, logs, dataset titles, and filenames;
* `R` may introduce ambiguity with run identifiers such as `R1` or `R2`.

Thus:

----
P1D
----

becomes:

----
1D
----

===== Alternative Relative Notations

Alternative notations such as:

----
D+1
D-1
T+2
T-6H
----

are recognised and may be familiar from other standards or operational contexts.

However, these forms are intentionally not used because:

* they rely on special characters that may require escaping or special handling in some tools;
* they are less suitable for consistent reuse in filenames, identifiers, and metadata values;
* compact alphanumeric identifiers improve portability and interoperability.

Thus:

----
D+1
----

is represented as:

----
D1
----

and:

----
D-1
----

is represented as:

----
1D
----

==== Guidance

The purpose of the `TimeHorizon` element is practical identification rather than formal temporal modelling.

Implementations should therefore prioritise:

* operational familiarity;
* naming consistency;
* deterministic interpretation;
* uniqueness;
* safe reuse across provenance metadata, dataset titles, and physical file names.

=== Run

The `Run` element identifies a planned repeated execution of the same activity within the same process and time horizon.

Its purpose is to distinguish formally defined iterations that are part of the business or operational process.

Examples include:

* first coordinated day-ahead security analysis;
* second coordinated day-ahead security analysis;
* multiple scheduled market or coordination runs within the same operational horizon.

The `Run` element shall only be used when repetition is an intentional part of the defined process.

It shall *not* be used to distinguish:

* technical retries due to failed execution;
* retransmission of corrected data;
* resubmission of improved or updated datasets;
* replacement of previously published data.

Such cases represent correction, replacement, or retransmission events and should be handled through dataset versioning, provenance metadata, or process-specific mechanisms rather than by incrementing the run identifier.

==== Naming Convention

The format shall be:

----
R<run number>
----

Where:

* `R` identifies the run qualifier;
* `<run number>` identifies the planned iteration number within the same process and time horizon.

Examples:

[cols="1,3",options="header"]
|===
| Value | Meaning

| R1
| First planned execution of the activity

| R2
| Second planned execution of the activity

| R3
| Third planned execution of the activity
|===


=== Naming Rules

The following rules apply:

* The activity identifier shall represent the generating activity.
* The same profile may be generated by different activity types.
* Multiple profiles may be generated by the same activity.
* The activity identifier shall not be derived solely from profile names.
* Optional elements shall only be included when needed to distinguish activities.
* Implementations shall use a consistent naming vocabulary.

=== Notes

`prov:wasGeneratedBy` identifies the generating activity and shall not be interpreted as a file naming convention.

File names and dataset titles may reuse the same identifier for consistency, but operational semantics shall be derived from metadata rather than parsing file names.
